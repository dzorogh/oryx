topic: Redesign of responsive create-transfer dialog
updated: 2026-09-20T15:27
---

- (decision) Use coaching path and design a responsive dialog for desktop and mobile.
- (decision) Use ProductionFromOrderForm as the structural reference: wide dialog, compact line table, summary, and separate footer.
- (decision) User-facing labels in the proposed UI are English; UX documentation remains Russian.
- (event) Imported user screenshot as imports/current-transfer-dialog.png.
- (decision) Primary protagonist is a logistics coordinator.
- (decision) Typical transfer contains 4–10 product lines.
- (decision) Free and customer-order-reserved quantities are frequently mixed, so allocation must remain visible and editable without dominating every row.
- (decision) Desktop is the primary creation surface; phone creation is occasional but must remain fully usable.
- (decision) Creation is launched both from the Transfers list and from a customer order; both entries should share one UX pattern.
- (decision) The primary confidence check before submission is that requested quantities do not exceed source-warehouse availability.
- (decision) Scope covers the shared creation pattern for list and customer-order entry points; transfer detail is out of scope.
- (decision) Customer-order entry: select order lines and quantities; customer-order allocation is implicit, no separate allocation control; save as Draft rather than sending immediately.
- (decision) Transfers-list entry moves free stock only; no customer-order allocation control appears in this variant.
- (decision) Products are added through an Add product action that inserts a new editable row.
- (assumption) Accessibility follows the inherited shadcn floor: keyboard-complete dialog and table controls, visible focus, programmatic labels, inline error association, and no color-only status.
- (assumption) Primary theme is the existing Oryx light UI; responsive behavior is specified, while dark mode and offline behavior add no custom UX delta.
- (decision) Chosen visual direction: Dense Ledger. Use a wide, data-dense desktop table and a compact but fully usable mobile list; discard Route First and Guided Table.
- (decision) Expected end is optional in both entry contexts.
- (decision) Desktop product table shows both On hand and Available before the editable Move quantity.
- (decision) Named journey: Marina, logistics coordinator, starts from Transfers or OMS-120; sets WH-1 to WH-2 and optional expected end; adds 4–10 lines; reads On hand and Available before Move; resolves inline over-limit errors; reviews route and composition; creates a Draft. In OMS-120 context, selected quantities retain that order allocation implicitly.
- (decision) After successful Draft creation, navigate directly to the new transfer detail page.
- (decision) Dirty close uses an in-dialog confirmation for every close channel: Keep editing is the safe default; Discard changes is destructive; focus returns predictably.
- (override) Remove transfer Draft entirely. Both list and customer-order creation submit one atomic create-and-send operation, resulting directly in Sent; Draft status, Draft creation actions, and post-create Draft editing are no longer part of the transfer UX.
- (decision) Existing transfer Draft rows are demo data and may be cleared; no legacy migration UX is required.
- (change) Submission now calls one transactional, idempotent create-and-send operation that validates current availability, creates the transfer and lines/allocations, posts stock movement, sets status Sent, and returns the transfer id for navigation.
- (decision) Availability formulas: On hand is physical source-warehouse quantity across free and reserved owners; Available is free/null-owner quantity for generic entry and current-order reserved quantity for customer-order entry.
- (decision) After successful create-and-send, navigate to the new transfer detail in Sent state. Transfer lines are not editable after submission.
- (override) Existing demo Draft transfers must be migrated to Sent through store_send_transfer rather than cleared. Current live demo snapshot has no Draft rows, so the backfill is presently a no-op but remains part of the migration contract.
