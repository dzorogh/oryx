- (direction by user) ИИ выбирает четыре техники; режим Creative Partner
- (decision) Порядок: Concept Blending, Analogical Thinking, First Principles Thinking, Morphological Analysis
- (technique) started Concept Blending
- (idea by user) RSV и REL почти идентичны; можно назвать одним словом и менять только знак или направление
- (idea by coach) Гибрид: allocation — один posted документ со знаком +1/−1 на оси free↔reserved; код один, эффект определяется sign
- (question by user) Пока нет названия единого документа
- (idea by coach) Кандидаты имени: allocation, reserve, hold, claim, stock hold, reservation movement
- (direction by user) Название единой сущности брать из практики других систем
- (idea by coach) Кандидаты из ERP/WMS: allocation, reservation, reservation adjustment, inventory reservation, hold, commitment, reserve movement
- (decision by user) Единая сущность называется Reservation
- (idea by coach) Снятие брони = Reservation с отрицательным количеством или direction=release, без отдельного типа документа
- (question by user) Как лучше задавать знак: отрицательное qty или явное направление?
- (insight by coach) В ERP/WMS чаще: qty всегда > 0 + явный movement type/direction; отрицательное qty редко в документах, чаще только в журнале проводок
- (question by user) Как обычно моделируют направление: отрицательное qty или явное поле reserve/release
- (idea by coach) Типовой вариант: в бизнес-документе operation=reserve|release и положительное qty; знаковые дельты остаются только во внутреннем складском журнале
- (insight by coach) Явное направление делает документ читаемым и не допускает двойного отрицания release с отрицательным qty
- (decision by user) Reservation содержит явное operation=reserve|release; qty всегда положительное
- (technique) started Analogical Thinking
- (idea by coach) Банковская аналогия: Reservation — перевод количества между счетами free и reserved(order); reserve переводит туда, release обратно, исходная операция не отменяется
- (insight by coach) Одна таблица документов и строк может обслуживать оба направления, а журнал остаётся неизменяемым
- (decision by user) Одна Reservation может содержать несколько товаров, но только одно место
- (idea by coach) Место переносится из строк в заголовок: Reservation = order + location + operation + many product lines
- (insight by coach) Единое место в заголовке устраняет повтор location_type/location_id в каждой строке и упрощает проверки остатка
- (decision by user) Все строки одной Reservation относятся к одному customer_order_id и одному location
- (idea by coach) Строке Reservation достаточно customer_order_line_id + qty; product_id выводится из строки заказа и не дублируется
- (insight by coach) Ссылка на строку заказа одновременно фиксирует заказ и товар и предотвращает несовпадение product_id
- (decision by user) Reservation line не хранит product_id; товар выводится через customer_order_line_id
- (technique) started First Principles Thinking
- (idea by coach) Минимальный lifecycle Reservation: draft для редактирования и posted для неизменяемой операции; cancelled не нужен
- (decision by user) Reservation имеет только статусы draft и posted; posted неизменяем, cancelled отсутствует
- (idea by coach) Release-specific reason заменяется единым необязательным note в заголовке Reservation для обоих направлений
- (decision by user) Reservation имеет необязательную заметку note для обоих направлений
- (idea by coach) Единая сущность использует одну нумерацию и префикс RSV; направление показывается operation, а REL-код исчезает
- (decision by user) Одна последовательность кодов RSV для reserve и release; префикс REL удаляется
- (technique) started Morphological Analysis
- (idea by coach) operation хранится в заголовке и применяется ко всем строкам; смешивать reserve и release в одном документе нельзя
- (decision by user) operation задаётся в заголовке; все строки Reservation имеют одно направление
- (idea by coach) Не вводить семантику полной отмены: release принимает любое положительное qty не больше текущего резерва; частичность получается из обычного количества
- (decision by user) Release допускает любое положительное qty до текущего резерва; отдельного режима полной отмены нет
- (idea by coach) Reservation работает только в местах с free/reserved: warehouse, production_order_line, transfer; customer_order/shipped исключён
- (decision by user) Reservation location ограничен warehouse, production_order_line или transfer; shipped/customer_order не участвует
- (question) При закрытии заказа резерв может находиться в нескольких местах, а одна Reservation допускает только одно место
- (question by user) Какие варианты снятия распределённого резерва при закрытии заказа и какой чаще применяется
- (idea by coach) Вариант A: закрытие создаёт отдельную posted Reservation(operation=release) для каждого места в одной транзакции
- (idea by coach) Вариант B: разрешить одной Reservation несколько мест и сохранить location в строках
- (idea by coach) Вариант C: блокировать закрытие заказа, пока менеджер вручную не снимет весь резерв
- (insight by coach) Чаще применяется автоматическая deallocation при отмене/закрытии заказа; для выбранной схемы это один release-документ на место, созданные атомарно и показанные пользователю
- (decision by user) При закрытии заказа одна транзакция создаёт отдельную posted Reservation(operation=release) для каждого места с остатком резерва
- (idea by coach) Автоматически созданной Reservation нужен явный origin=manual|order_close, чтобы БД объясняла причину без догадок и свободного текста
- (decision by user) Reservation содержит origin=manual|order_close; note остаётся необязательным
- (idea by coach) Единая таблица поддерживает единый список Reservations с фильтром operation; отдельный раздел Releases и префикс REL исчезают
- (decision by user) UI объединяется: один раздел Reservations, фильтр All/Reserve/Release, одна карточка; Releases и REL удаляются
- (question) Нужно решить миграцию существующих RSV/REL: сохранять записи или пересоздать демо-данные
- (decision by user) Существующие демо RSV/REL можно не мигрировать; допустим reset/reseed новой единой схемы
- (insight) Четыре техники пройдены; определены имя, направление, схема заголовка/строк, lifecycle, origin, UI и стратегия перехода
- (technique) started PMI convergence
- (insight by coach) PMI pluses: одна пара таблиц, форма, список, нумерация и posting path; направление явно; product/location duplication removed
- (insight by coach) PMI minuses: Reservation(operation=release) звучит менее естественно; закрытие распределённого заказа создаёт несколько документов; reset demo data
- (insight by coach) PMI interesting: бизнес-документ хранит operation и positive qty, а signed deltas остаются только в ledger
- (decision by user) Предыдущее решение о reset отменено: существующие демо RSV/REL нужно мигрировать в единую Reservation
- (idea by coach) Миграция группирует строки старого документа по location; документ с несколькими местами раскладывается в несколько новых Reservation
- (idea by coach) Старые RSV копируются как operation=reserve, REL как operation=release; ledger source_type/source_id переназначаются через временную таблицу соответствий без изменения балансов
- (decision by user) Миграция сохраняет бизнес-данные, связи и ledger; старые numeric IDs и REL-коды могут измениться на новые RSV-n
- (decision) Итоговый кандидат принят с миграцией существующих демо-данных
- (decision by user) Все зафиксированные решения обязательны для реализации
- (insight) Объединение должно охватить schema, posting RPC, ledger source identity, numbering and UI; иначе две модели сохранятся скрыто
- (insight) operation+positive qty даёт симметричные проверки: reserve ограничен free/open demand, release ограничен reserved выбранного order line/location
- (insight) one-location header требует при миграции split старых multi-location документов и при order_close — один новый документ на место
