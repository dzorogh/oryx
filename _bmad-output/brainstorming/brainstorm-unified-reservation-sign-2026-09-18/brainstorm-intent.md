# Intent: единая модель Reservation

## Цель

Заменить отдельные модели RSV и REL единой сущностью `Reservation`, в которой направление изменения резерва задаётся операцией, а количество всегда остаётся положительным.

## Итоговая модель

### Заголовок Reservation

- `customer_order_id` — один заказ на документ.
- `location` — одно место на документ.
- `operation` — `reserve` или `release`; применяется ко всем строкам.
- `status` — только `draft` или `posted`.
- `origin` — `manual` или `order_close`.
- `note` — необязательная заметка для обоих направлений.
- `code` — единый код с префиксом `RSV` и общей последовательностью для `reserve` и `release`; префикс `REL` удаляется.

### Строка Reservation

- `customer_order_line_id`.
- `qty`, всегда больше нуля.
- `product_id` не хранится: товар определяется через строку заказа.

### Допустимые места

`location` может быть только одного из типов:

- `warehouse`;
- `production_order_line`;
- `transfer`.

`customer_order` и `shipped` в Reservation не участвуют.

## Поведение

- `reserve` переводит указанное количество из свободного остатка в резерв выбранной строки заказа и места.
- `release` возвращает указанное количество из резерва в свободный остаток.
- Частичное снятие резерва задаётся обычным положительным `qty`; отдельного режима полной отмены нет.
- `draft` можно редактировать.
- `posted` представляет неизменяемую операцию.
- При закрытии заказа одна транзакция создаёт отдельную `posted` Reservation с `operation=release` и `origin=order_close` для каждого места, где остаётся резерв.

## UI

- Один раздел **Reservations**.
- Единый список с фильтром **All / Reserve / Release**.
- Одна карточка Reservation для обоих направлений.
- Отдельный раздел Releases и обозначение REL удаляются.

## Миграция

- Существующие RSV мигрируют в Reservation с `operation=reserve`.
- Существующие REL мигрируют в Reservation с `operation=release`.
- Старый документ с несколькими местами разделяется на отдельную Reservation для каждого места.
- Бизнес-данные, связи и ledger сохраняются.
- `ledger source_type/source_id` переназначаются на новые Reservation через временное соответствие без изменения балансов.
- Старые numeric ID и коды могут измениться; все новые документы получают коды единой последовательности `RSV-n`, включая бывшие REL.
- Переход должен одновременно охватить схему, posting RPC, идентичность источника в ledger, нумерацию и UI.

## Инварианты

- Каждая Reservation относится ровно к одному заказу, одному месту и одной операции.
- Все строки относятся к `customer_order_id` заголовка.
- Все строки используют `location` и `operation` заголовка; смешение мест или направлений внутри документа запрещено.
- Каждая строка ссылается на строку заказа и не дублирует `product_id`.
- `qty > 0` для обеих операций; знаковая дельта существует только во внутреннем ledger.
- Допустимы только статусы `draft` и `posted`; статуса `cancelled` нет.
- `posted` Reservation неизменяема.
- `release` не может превышать текущий резерв выбранной строки заказа в выбранном месте.
- `reserve` не может превышать доступный свободный остаток и открытую потребность строки заказа.
- Закрытие заказа снимает распределённый резерв отдельными документами по местам в одной транзакции.
- Миграция ledger не изменяет итоговые балансы.

## Обязательные проверки

- Валидировать `operation` как `reserve|release`, `status` как `draft|posted`, `origin` как `manual|order_close`.
- Валидировать положительный `qty` каждой строки.
- Проверять принадлежность каждой `customer_order_line_id` заказу из заголовка.
- Проверять допустимый тип `location`.
- При posting `reserve` проверять свободный остаток и открытую потребность.
- При posting `release` проверять текущий резерв по сочетанию строки заказа и места.
- Запрещать изменение `posted` документов.
- Проверять атомарность создания release-документов при закрытии заказа.
- После миграции проверять корректность split по местам, переназначение ledger-источников и неизменность балансов.
