## 1. Постановка (U)

Дословно:

> Экран распределения потребностей заказа.
> Остатки на странице заказа клиента, чтобы сразу можно было прикинуть, сделать предварительный документ резервирования. Сначала из остатков набрать, потом из заказов на производство и видно план. В плане можно сразу запланировать резервы (где угодно), отгрузки, перемещения, производства. Чтобы было можно сразу прикидывать, менять, редактировать. Драфт резерва, драфт заказа на производство. Потом драфты становятся полноценными документами.
> План сохраняется когда мы закрываем страницу или заказ, чтобы потом вернуться. План брони не создает, никакие документы не делаем.
> План может стать неактуальным в любой момент. Нужно подсвечивать расхождения и не давать сохранять/запускать план если там есть несостыковки.
> Сразу в плане сделать минус (рассинхрон) нельзя, можно его только …
> — Можно планировать изменения других резервов.
> — Нужно показывать предварительный результат.
> — Инпуты рядом с каждой цифрой? или одна в строке?
> — Идеи Гордиенко (второстепенно): FRS 3.23 и 4.8A.

Нормализовано:

| ID | Требование |
|----|------------|
| U-1 | Отдельный экран (или режим) распределения потребностей одного заказа клиента. |
| U-2 | На странице заказа видны остатки, чтобы сразу прикинуть покрытие. |
| U-3 | Порядок набора: сначала из остатков, затем из заказов на производство. Итог виден как план. |
| U-4 | В плане можно запланировать резервы «где угодно» (склад, в пути, в производстве), отгрузки, перемещения, производство. |
| U-5 | План можно прикидывать, менять, редактировать много раз. |
| U-6 | В плане есть «черновик резерва» и «черновик заказа на производство». Позже они становятся настоящими документами. |
| U-7 | План сохраняется при закрытии страницы или заказа; к нему можно вернуться. |
| U-8 | План не создаёт брони и документы. |
| U-9 | План может устареть в любой момент; расхождения подсвечиваются. |
| U-10 | С несостыковками план нельзя «сохранять/запускать». |
| U-11 | Сразу сделать в плане минус (рассинхрон) нельзя; можно его только … (фраза оборвана). |
| U-12 | Можно планировать изменения чужих резервов (других заказов, регионов). |
| U-13 | Показывать предварительный результат (что будет после применения). |
| U-14 | Открытый UX-вопрос: поле ввода рядом с каждым числом или одно на строку. |
| U-15 | Сверить с FRS 3.23 / 4.8A, не упустить важное. |

## 2. Требования FRS (F)

### 2.1 Термины

- **Рабочее место исполнения** — контекстный экран одного заказа: потребность, доступные источники и черновик плана одновременно.
- **Черновик плана** — сохраняемый набор предварительных действий. Не меняет остаток, назначения, журнал и документы до применения.
- **Плановое покрытие** — количество в черновике, ещё не ставшее назначением или документом.
- **Зафиксированное покрытие** — количество, уже учтённое активным назначением или плановой долей существующего Draft/Waiting Payment документа, без двойного учёта.
- **Плановая доля** — часть позиции непроведённого документа, запланированная под заказ; складским фактом не является.

### 2.2 Экран (3.23, 4.8A)

| ID | Требование |
|----|------------|
| F-1 | Открывается из карточки заказа кнопкой «Управлять исполнением»; сохраняет контекст заказа. |
| F-2 | Одновременно видны: исходная потребность, фактическое исполнение, доступные источники, текущий черновик, непокрытый остаток. |
| F-3 | По каждой строке: заказано, зафиксированное покрытие, в черновике, осталось, в производстве, выпущено, в пути, отгружено, предупреждение/конфликт. |
| F-4 | Полностью покрытая строка не исчезает (остаток 0). Фильтры «Все / Не покрыто / Покрыто в плане / Есть конфликт». |
| F-5 | Раскладка desktop: закреплённый блок «Потребность заказа» + рабочая область с вкладками «Остатки», «Производство», «Перемещения», «Отгрузка», «План». |
| F-6 | Верхняя панель: номер, статус, срок, автор и время последнего изменения черновика; действия «Проверить план», «Применить план», «Очистить черновик», «Закрыть». |
| F-7 | Индикатор «Сохранение / Сохранено / Ошибка сохранения»; при ошибке — предупреждение о несохранённом при закрытии. |
| F-8 | Кнопка называется «Добавить в план». «Забронировать» / «Создать документ» — только после применения или в карточке созданного объекта. |
| F-9 | Экран предупреждает: план не блокирует остаток и не гарантирует доступность. |

### 2.3 Черновик плана

| ID | Требование |
|----|------------|
| F-10 | Хранится на backend; один общий текущий черновик на заказ. Повторное открытие восстанавливает действия. |
| F-11 | Каждое добавление / изменение / удаление действия сохраняется сразу, с optimistic version черновика. Закрытие экрана черновик не удаляет. |
| F-12 | Черновик не создаёт назначений, проводок, документов и не меняет фактический прогресс заказа. |
| F-13 | Удаление действия из черновика не вызывает release или отмену документа. |
| F-14 | «Очистить черновик» — с подтверждением; удаляет только предварительные действия. |
| F-15 | Устаревшая версия черновика (правил другой пользователь) — сохранение отклоняется, UI грузит актуальный черновик, без автослияния. |
| F-16 | Версии заказа и источников проверяются при проверке и применении, а не блокируют обычное сохранение. |
| F-17 | Изменение заказа или источника делает несовместимые действия конфликтными; они сохраняются для разбора, их можно изменить или удалить. |
| F-18 | После применения черновик становится read-only результатом; при остаточной потребности можно начать новый. |
| F-19 | Для завершённого / отменённого заказа экран read-only: факты и применённые планы, без нового черновика. |

### 2.4 Источники и количества

| ID | Требование |
|----|------------|
| F-20 | Источники автоматически ограничены товарами заказа и допустимыми правилами (завод, маршрут, хабы). |
| F-21 | Количество по умолчанию = min(доступно в источнике, остаточная потребность строки); менеджер может уменьшить. |
| F-22 | Осталось = max(0, заказано − зафиксированное покрытие − доли черновика). Сумма долей черновика ≤ непокрытой потребности. |
| F-23 | Один источник нельзя использовать в нескольких действиях сверх его доступного количества. |
| F-24 | Свободная доля заказа на производство в покрытие заказа не входит. |
| F-25 | На вкладке остатков можно показать количество, назначенное другим заказам; доступным источником оно не считается. |

### 2.5 Действия плана

| ID | Действие | Условие |
|----|----------|---------|
| F-26 | Назначить свободный остаток на складе | — |
| F-27 | Назначить свободную долю активного заказа на производство | PO в Production |
| F-28 | Назначить свободную долю перемещения в пути | transfer In Transit |
| F-29 | Создать Draft заказа на производство | стратегии «Произвести остаточную потребность» и «Произвести весь выбранный объём»; вторая не трогает свободный остаток |
| F-30 | Создать Draft перемещения | только при существующем физическом источнике |
| F-31 | Создать отгрузку | весь состав на одном допустимом складе и после предыдущих действий плана полностью назначен заказу |
| F-32 | Перебронирование с другого заказа | причина, подтверждение; видно затронутый заказ, срок, переносимое количество и возникающий дефицит |
| F-33 | Выпуск производства из плана не создаётся | выпуск — только из заказа на производство |
| F-34 | «Следующие действия» | будущие перемещение/отгрузка без предусловий показываются отдельным блоком, в применяемый план не входят |

Запреты перебронирования (F-32): отгруженное; завершённый заказ или заказ с неотменённой отгрузкой; неактивное место; не тот завод; не та категория/маршрут/хаб; сверх остаточной потребности целевого заказа.

### 2.6 Проверка и применение

| ID | Требование |
|----|------------|
| F-35 | «Проверить план» — ручной запуск; та же проверка автоматически при «Применить план». |
| F-36 | Проверка перечитывает заказ, версии источников, доступное количество, состояния документов, завод, маршрут, хабы, предусловия отгрузки. |
| F-37 | Ошибки — рядом с конкретными строками и действиями. Черновик сохраняется, ничего не выполняется. |
| F-38 | «Применить план» — одна идемпотентная команда, всё или ничего: назначения, Draft-документы, перебронирование, версии, история, уведомления. |
| F-39 | После применения — список созданных объектов со ссылками «Открыть». Ошибка применения ничего не показывает созданным. |
| F-40 | Уведомления клиенту — только после применения; сохранение и очистка черновика уведомлений не шлют. |
| F-41 | Плановые доли созданного Draft/WP заказа на производство входят в зафиксированное покрытие и не дают повторно запланировать то же количество. |
| F-42 | Экран «Брони» остаётся отдельной очередью непосредственных операций; действия черновика не вызывают его команд. |

### 2.7 Use case UC-2 (сжато)

Открыть → на «Остатках» добавить свободное в план → на «Производстве» «Произвести остаточную потребность» → вкладка «План» → «Проверить план» → «Применить план» → ссылки на созданное. Альтернативы: закрыли до применения (черновик жив); количество занял другой (конфликт у действия, ничего не создано); производить всё независимо от остатка; отгрузка пока невозможна (следующие действия); перебронирование; одно действие не прошло проверку; заказ готов к отгрузке.

## 3. Структура данных Oryx (S) — источник правды

Состояние на 24.09.2026: миграции `supabase/migrations/` = живая база (таблицы, колонки, функции сверены запросом). Все таблицы — `public.store_*`.

### 3.1 Реестры: место, владелец, документ

| Таблица | Поля | Смысл |
|---------|------|-------|
| `store_stock_location` | `id`, `kind` ∈ `warehouse / production_order / transfer / customer_order` | Место количества. Каждый склад, заказ на производство, перемещение и заказ клиента получает своё место при создании. |
| `store_stock_owner` | `id`, `kind` ∈ `free / customer_order / region` | Владелец количества. `free` — один на всю базу (id=1). Каждый заказ клиента и каждый регион получают своего владельца. |
| `store_document` | `id`, `kind`, `sequence_number`, `description`, `status`, `expected_end_on`, `created_at`, `created_by` | Общий реестр документов. Номер = префикс вида + `sequence_number`. |
| `store_document_kind` | `code`, `number_prefix`, `display_name`, `has_lifecycle`, `allowed_statuses` | Виды: `customer_order` OMS, `production_order` PO, `transfer` TR — со статусами `draft / in_progress / done / cancelled`; `production_output` OUT — `draft / done / cancelled` (`draft` в интерфейсе «Запланирован»); `reservation` RSV, `shipment` SHP, `adjustment` ADJ — без статуса. |
| `store_document_history` | `document_id`, `status`, `expected_end_on`, `changed_at`, `changed_by` | Снимки статуса и срока. Пишет только триггер; неизменяема. |
| `app_user` | `id`, `name` | Один демо-пользователь (id=1), `store_current_user_id()` всегда 1. |

### 3.2 Подтипы документов

| Таблица | Поля | Смысл |
|---------|------|-------|
| `store_customer_order` | `region_id`, `stock_location_id`, `stock_owner_id` | Заказ клиента: регион (цена dealer), своё место «отгружено клиенту», свой владелец для резервов. |
| `store_production_order` | `plant_id`, `stock_location_id` | Заказ на производство: план на заводе. Его место существует, но проводок на нём нет. |
| `store_production_output` | `production_order_id` | Выпуск по заказу на производство; кладёт товар на склад завода (`store_plant.warehouse_id`). |
| `store_transfer` | `from_warehouse_id`, `to_warehouse_id`, `stock_location_id` | Перемещение; его место = «в пути». |
| `store_reservation` | `location_id`, `owner_id` (владелец-назначение), `creation_source`, `posted_at` NOT NULL | Резерв: всегда проведён. `creation_source` ∈ `manual / customer_order_close / production_order_close`. |
| `store_shipment` | `from_location_id`, `to_location_id` | Отгрузка (склад → место заказа) или возврат (место заказа → склад). |
| `store_adjustment` | `location_id` | Корректировка свободного остатка склада, строки со знаком. |

### 3.3 Строки и журнал

| Объект | Поля | Смысл |
|--------|------|-------|
| `store_document_product_line` | `document_id`, `product_variant_id`, `quantity` numeric(18,2), `from_owner_id`, `to_owner_id`, `variant_name`, `unit_price`, `currency_id` | Единая товарная строка всех видов. Уникальна по `(document, variant, from_owner, to_owner)`. Цена снимается при вставке: заказ клиента — dealer региона, заказ на производство — purchase. |
| `store_stock_transaction` | `product_variant_id`, `quantity` (знак), `location_id`, `owner_id`, `document_id`, `created_at` | Журнал, только добавление. Пишется лишь командами под advisory lock `(variant, location, owner)`. |
| `store_stock_balance` (view) | `product_variant_id`, `location_id`, `owner_id`, `quantity` | Остаток = сумма журнала, нули скрыты. `store_stock_balance_ref` добавляет вид места / владельца, сущность и состояние `free / reserved / shipped`. |

Каталог: `store_product` → `store_product_variant` (`name`, `unit`, `plant_id`, `image_url`; SKU удалён миграцией `20260923143000`). Склад `store_warehouse` (одно место), завод `store_plant` (ровно один склад). Регион `store_region` (свой владелец, валюты). Справочники удаляются только мягко (`deleted_at`).

### 3.4 Как количество живёт в документах

| Документ | Что пишет строка | Когда появляется проводка |
|----------|------------------|---------------------------|
| Заказ клиента | `quantity` = потребность товара; владельцев нет | Никогда |
| Заказ на производство | `quantity` = план товара на заводе; владельцев нет | Никогда (место без проводок) |
| Выпуск `draft` | строки по владельцу: `to_owner_id` = free, заказ клиента или регион | Нет — это плановый «резерв в выпуске». В интерфейсе статус называется «Запланирован» |
| Выпуск `done` | те же строки | + на склад завода с владельцем строки |
| Перемещение | `from_owner = to_owner` = владелец доли | При создании: склад отправления → место «в пути»; при `done`: «в пути» → склад назначения, владелец сохраняется |
| Резерв | `from_owner_id` на строке (free, регион или другой заказ); назначение в шапке | Сразу: перенос между владельцами на том же месте (склад или «в пути») |
| Отгрузка | `from = to` = владелец заказа | Сразу: склад → место заказа клиента |

### 3.5 Команды (RPC), доступные приложению

| Команда | Что делает | Ограничения |
|---------|-----------|-------------|
| `store_create_customer_order` | Создаёт заказ сразу `in_progress` | Черновика заказа нет; товар в заказе встречается один раз |
| `store_close_customer_order` | `done` + автоснятие резервов заказа на складах и «в пути» документами RSV `customer_order_close` | — |
| `store_create_production_order` | Заказ `draft` или `in_progress`, строки плана | Завод обязателен |
| `store_set_order_line_quantity` | Задаёт абсолютное количество товара в заказе клиента или заказе на производство: нет строки — вставка, есть — замена количества, 0 — удаление | Любой статус документа. Интерфейс при повторном добавлении того же товара суммирует количество в одну строку. Цена — снимок первой вставки. Заказ клиента не ниже отгруженного; удаление строки заказчика запрещено, пока есть отгрузка, складской резерв или резерв в запланированном выпуске. Удаление строки плана запрещено, пока товар есть в неотменённых выпусках; план может стать меньше выпусков |
| `store_set_production_status` | `draft ↔ in_progress` | `done` — только через закрытие |
| `store_close_production_order` | `done`, активные выпуски отменяются | Резервы в них исчезают |
| `store_create_production_output` | Выпуск; `p_complete=false` → запланированный выпуск (`draft`); на строке владелец и `allocation_quantity` (остаток идёт в свободно) | Сумма неотменённых выпусков ≤ плана |
| `store_move_in_production_output` / `store_reserve_in_production_output` | Перенос количества между владельцами внутри запланированного выпуска (любой → любой) | Только `draft`; `done` не меняется |
| `store_complete_production_output` | `done` + проводки на склад завода | — |
| `store_create_and_post_reservation` | Резерв: место склад или «в пути», назначение, строки с источником-владельцем | Проверяется только остаток источника; превышение открытой потребности целевого заказа база не проверяет (проверяет интерфейс) |
| `store_create_and_send_transfer` | Перемещение сразу `in_progress`, списание со склада отправления | Черновика перемещения в базе нет |
| `store_complete_transfer` | Приёмка всего в пути | Частичной приёмки нет |
| `store_create_and_post_shipment` | Отгрузка / возврат, сразу проведена | Нужен резерв заказа на складе; частичная отгрузка допустима |
| `store_create_and_post_adjustment` | Корректировка свободного остатка | Описание обязательно |
| `store_cancel_document` | Отмена документа со статусом | Нельзя: резерв, отгрузку, корректировку, отправленное перемещение, выпуск `done` |
| `store_update_expected_end` | Срок документа | Не для завершённых |

У выпуска нет статуса `in_progress`.

### 3.6 Защиты и соглашения

- Браузер: только SELECT и перечисленные команды (anon, без входа). Прямой INSERT / UPDATE / DELETE запрещён RLS и грантами.
- Документы не удаляются (триггер). Шапка завершённого или отменённого документа не меняется. Строки заказа клиента и заказа на производство меняются при любом статусе. Строки резерва, отгрузки и корректировки после создания не меняются; строки отправленного перемещения и завершённого выпуска — тоже.
- Журнал и история неизменяемы.
- Версий документов, ключей идемпотентности, outbox, авторизации нет.
- Чтение страницы — одна read-RPC; карточка заказа — `store_document_context('customer_order', ref)`: документ, связанные документы, их строки и история, проводки и остатки `balances` по товарам заказа.

### 3.7 Производные показатели (функции)

- `store_po_plan_qty` — план товара в заказе на производство.
- `store_po_output_qty` — в неотменённых выпусках; `store_po_produced_qty` — в выпусках `done`.
- `store_po_assigned_qty` — занято владельцами (не free) в выпусках `draft`.
- Незанятый план заказа на производство = план − неотменённые выпуски. Это колонка «Не распределено» в календаре; строки владельца у такого количества нет.

## 3А. Текущий интерфейс Oryx (O)

| ID | Факт |

Действия этапов выполняются сразу: «Новый заказ на производство», «Зарезервировать в выпуске», «Выпустить», «Переместить занятое», «Зарезервировать в пути», «Отгрузить», «Зарезервировать». |

## 4. Расхождения

| ID | Где | Суть |
|----|-----|------|
| C-1 | U-6 ↔ S 3.2 | «Черновик резерва», а в схеме резерв всегда проведён (`posted_at` NOT NULL, черновики удалены). Черновик резерва может жить только в плане — в новой таблице, не в `store_reservation`. |
| C-2 | F-27, F-41 ↔ S 3.4 | В FRS производственное покрытие — доли в строках заказа на производство. В схеме у строк заказа на производство нет владельцев; покрытие держат строки запланированного выпуска. Значит «произвести под заказ» при применении = заказ на производство + запланированный выпуск с владельцем (или строка в существующем запланированном выпуске). |
| C-3 | U-10 ↔ F-11, F-17 | Постановка: «не давать сохранять» план с несостыковками. FRS: черновик сохраняется всегда, конфликты помечаются, блокируется только применение. |
| C-4 | U-2 ↔ F-1, F-5 | Остатки прямо на странице заказа или отдельный экран-рабочее место? |
| C-5 | U-4 ↔ S 3.5 | Перемещение и отгрузка в схеме не имеют черновика: создание сразу двигает товар (перемещение уходит в путь, отгрузка списывается). Если план их «применит», это физическое действие, а не документ-черновик. Нужно решить: применять их из плана, держать как «следующие действия» или добавить черновик перемещения (статус `draft` в словаре уже есть, команды нет). |
| C-6 | U-12 ↔ S 3.5 | Схема уже умеет перебронировать: строка резерва с `from_owner_id` = другой заказ или регион; в черновике выпуска — перенос между любыми владельцами. Вопрос — какие изменения чужих резервов разрешать в плане и с каким подтверждением. |
| C-7 | S 3.5 ↔ F-31 | Частичная отгрузка допустима в схеме, в FRS — только полная. |
| C-8 | O-1 ↔ F-42 | Что будет с прямыми действиями на карточке заказа: остаются, прячутся или переезжают в план? |
| C-9 | S 3.1 ↔ F | В схеме есть владелец «регион». Источник плана — только свободное или также региональный резерв (и чужие заказы)? Может ли план резервировать под регион? |
| C-10 | U-11 | Оборванная фраза про минус / рассинхрон. |
| C-11 | S 3.6 ↔ F-15, F-16, F-38 | Версий, идемпотентности и outbox в схеме нет. Для плана нужна своя версия (или отказ от неё); атомарность применения — одна RPC-транзакция. |
| C-12 | F-33 ↔ O-1 | «Выпустить» с карточки заказа — в FRS запрещено из плана. |
| C-13 | S 3.5 | Закрыто: `store_set_order_line_quantity` меняет, добавляет и удаляет строку заказа клиента и заказа на производство при любом статусе. Изменения строк в историю не пишутся, версий нет — план должен сам снимать количества строк, чтобы заметить, что они изменились. |
| C-14 | S 3.5 ↔ F-27 | Резерв «в производстве» в схеме — только в запланированном выпуске (`draft`). Незанятый план заказа на производство владельца не имеет. «Назначить свободную долю активного заказа на производство» = создать запланированный выпуск из незанятого плана или перенести свободное в имеющемся выпуске. |
| C-15 | S 3.5 | Открытую потребность целевого заказа при резерве база не проверяет. Проверка «не больше, чем нужно заказу» для плана — в новой команде применения. |

## 5. Вопросы по уровням (повестка брейншторма)

1. **Зачем и где.** Какую работу менеджера закрывает экран; чем отличается от карточки заказа и «Резервов»; страница или отдельный экран; один ли план на заказ.
2. **Жизненный цикл плана.** Черновик → проверка → применение; что значит «сохранять» и «запускать»; можно ли применять частями; что становится с планом после применения; история планов.
3. **Действия плана.** Полный список типов, какие документы и в каких статусах создаются; порядок; черновик заказа на производство и выпуска; перемещение и отгрузка без физических предусловий; чужие резервы и регионы.
4. **Актуальность.** Какие изменения мира ломают план; когда пересчитываем (при открытии, опросом, при проверке); как подсвечиваем; что именно блокируется; минус / рассинхрон.
5. **Предварительный результат.** Что показываем «после применения»: по строкам заказа, по источникам, по чужим заказам.
6. **UX-мелочи.** Поля ввода у каждой цифры или одно на строку; значения по умолчанию; «набрать автоматически»; фильтры; пустые состояния; подписи.
7. **Структура данных.** Только доработка схемы из раздела 3: где хранить план (новая таблица или новый вид документа), как действие плана ссылается на место, владельца и документ-источник, что снимать для обнаружения расхождений, какие RPC добавить (чтение, сохранение, проверка, применение) и как применение ложится на существующие команды.
