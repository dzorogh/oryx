# Intent: единая модель отгрузок и возвратов

> Главная ценность: **«интерфейс единый, но намерение всегда явно видно»**.

## Цель

Объединить отгрузки и возвраты в один тип товарного документа, не обезличивая пользовательское намерение. Модель покрывает только физическое движение между складом и заказом и непосредственное назначение возвращённого остатка; приёмка, оценка состояния, обмен и деньги находятся вне сценария.

## Итоговая доменная модель

- Один документ, общий список и общая последовательность номеров для отгрузок и возвратов.
- Заголовок задаёт заказ и физический маршрут `fromPlace → toPlace`.
- Допустимы только два маршрута:
  - `warehouse → customer_order` — **Отгрузка**;
  - `customer_order → warehouse` — **Возврат**.
- Направление вычисляется из маршрута и отдельно не хранится.
- Строка содержит товар, положительное количество и назначение остатка (`destination owner`).
- Документ не ссылается на исходную отгрузку или её строки. Для возврата можно выбрать любой склад.
- Черновиков и `status` нет: существование документа означает, что он проведён. Создание документа и его проводок — одна атомарная операция.
- Проведённый документ неизменяем. Корректировка выполняется новым документом обратного физического направления.

## Инварианты документа и строк

- Любое число частичных отгрузок и возвратов допустимо, пока исходная точка содержит достаточный текущий остаток.
- Количество всегда положительное; эффект определяется физическим маршрутом.
- Отгрузка может списывать только резерв текущего заказа на выбранном складе.
- Возврат может списывать только фактический shipped-баланс текущего заказа и товара в `customer_order`.
- Для отгрузки source и destination owner фиксированы текущим заказом.
- Для возврата source owner фиксирован текущим заказом, а destination owner выбирается по строке.
- Один товар в возврате можно разделить между несколькими строками с разными назначениями. Уникальность строки: документ + товар + destination owner; суммарное количество товара ограничено его текущим shipped-балансом.

## Поведение отгрузки

- Пользователь выбирает заказ и единственный склад-источник.
- Документ переносит зарезервированный за заказом товар со склада в `customer_order`.
- Свободный или региональный остаток нельзя отгрузить напрямую: сначала его нужно зарезервировать под заказ.

## Поведение возврата

- Пользователь выбирает заказ и склад-получатель, не обязательно склад исходной отгрузки.
- Документ переносит товар из `customer_order` на выбранный склад.
- Для каждой строки пользователь выбирает дальнейшую судьбу остатка:
  - `Free`;
  - текущий `Order`;
  - любой выбранный `Region`.
- Прямое назначение другому заказу не поддерживается; оно выполняется отдельным Reservation.

## Reserve then Ship

- Это явное составное действие по желанию пользователя: сначала отдельный Reservation собирает остаток из выбранных `Free`/`Region` sources под заказ, затем создаётся отгрузка.
- До подтверждения UI показывает, какие количества и из каких owners будут зарезервированы, а затем какой объём будет отгружен.
- Reservation остаётся отдельным видимым документом.
- Сценарий намеренно неатомарен между документами: если Reservation успешен, а Shipment завершился ошибкой, созданный резерв сохраняется.
- UI раздельно сообщает об успехе Reservation и ошибке Shipment, показывает оставшийся резерв и предлагает повторить только отгрузку.

## UX списка, создания и просмотра

- Раздел называется **«Отгрузки и возвраты»**.
- Общий список показывает оба направления вместе и содержит фильтры **Все / Отгрузки / Возвраты**.
- В списке одна кнопка **«Новый документ»**.
- Первый шаг создания предлагает две крупные операции: **«Отгрузить»** и **«Принять возврат»**.
- После выбора намерение фиксируется. Сменить его можно только возвратом на первый шаг с очисткой формы.
- Выбор намерения меняет заголовок, схему **Откуда → Куда**, роли заказа и склада, состав полей строк и главный глагол действия.
- На форме и странице документа тип **«Отгрузка»** или **«Возврат»** должен быть заметен сразу; единая оболочка не должна визуально скрывать различие операций.

## Осознанные компромиссы

- Нет атрибуции возврата конкретной отгрузке; ограничение строится по текущему балансу заказа и товара.
- Правила строк асимметричны: у отгрузки owner фиксирован, у возврата назначение выбирается построчно.
- Один товар может повторяться в возврате из-за разных destination owners.
- Возврат не является строгим восстановлением прежнего состояния: пользователь явно определяет судьбу остатка и может выбрать другой склад или регион.
- Отсутствие черновиков упрощает жизненный цикл, но требует завершать валидацию до единственной атомарной команды создания.
- Reserve then Ship сохраняет прозрачность двух самостоятельных документов ценой предусмотренного частичного успеха.

## Уроки текущего Reservation

- Осознанный мультисточник сохраняется: destination owner находится в заголовке, source owner — в строках; один Reservation может собрать назначение из `Free` и нескольких региональных резервов.
- Намерение документа нельзя классифицировать по одной строке или отдельной паре owners: смешанный `Free/Region → Order` остаётся резервированием под заказ, а не «переназначением».
- Связанные документы и покрытие заказа должны учитывать только относящиеся к заказу строки, не приписывая ему весь смешанный документ.
- Контекстные ограничения формы должны быть настоящими инвариантами, а выбор товаров — соответствовать составу заказа.
- Проводка каждого документа требует защиты от повторного и конкурентного выполнения; составные сценарии не должны создавать дубли при повторе.
- Единая атомарная команда создания движения устраняет известный риск Reservation, где раздельные запросы create/lines/post оставляют черновик или создают дубль после retry.

## Нерешённое именование реализации

Пользовательское имя зафиксировано как **«Отгрузки и возвраты»**. Внутреннее имя сущности, таблицы и TypeScript-типа пока не выбрано и не должно диктовать термин интерфейса.
