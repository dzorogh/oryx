- (insight by coach) Риск: immutable snapshot в момент создания конфликтует с существующими draft/edit/add-line сценариями; атомарная фиксация требует определить единый момент заморозки документа

- (insight by coach) В текущей модели activation означает материализацию плана PO как свободного WIP-остатка в виртуальном месте production_order: sync пишет delta в stock_transaction, а activated_quantity запоминает уже записанную часть, чтобы повтор не удвоил остаток
- (insight by coach) Термин вводит в заблуждение: это не начало производства и не выпуск, а технический курсор материализации планового количества в складском журнале

- (insight by coach) activated_quantity и store_sync_production_activation тогда удаляются целиком; Production Order становится чистым планом, а Production Output создаёт фактический товар вместо потребления заранее материализованного WIP
- (insight by coach) Текущие резервы на location=production_order больше не могут быть обычным резервом физического остатка; будущая потребность и фактический складской остаток должны быть разделены
- (question by user) Запрошена рекомендация: куда помещать товар по факту производства
- (idea by coach) Для текущего scope Production Output должен сразу создавать фактический остаток на складе завода; отдельное место Производство нужно только при реальном промежуточном процессе WIP/QC/приёмки, которого сейчас нет
- (decision by user) Production Output создаёт фактический остаток сразу на складе завода; отдельного места Производство/WIP нет
- (insight by coach) Failure risk: сервер пока не имеет канонической таблицы трёх региональных цен и статусов; документный snapshot нельзя надёжно строить из клиентского Yjs/demo-состояния
- (idea by coach) До универсальных строк нужна текущая store_product_region_offer/price table; create-document RPC атомарно копирует из неё все существующие регионы в line_region_snapshot
- (decision by user) Региональный snapshot допускает отсутствующие цены как NULL и не блокирует создание документа
- (idea by coach) Создание документа должно одной RPC-транзакцией записывать store_document, typed header, product lines, allocations и все region snapshots; после commit строки и снимки immutable, status/expected date могут жить отдельно в header/history
- (insight by user) Плановые документы нельзя делать полностью неизменяемыми: после создания заказа на производство пользователь захочет добавлять товары и менять объёмы
- (idea by coach) Разрешить изменение плановых документов через immutable revisions: store_document сохраняет identity/number, store_document_revision фиксирует версии, product lines принадлежат версии; UI показывает latest, а проведённые операционные документы имеют одну frozen revision
- (question by user) Поставлено под сомнение, являются ли полные document revisions единственным способом редактировать плановые документы
- (insight by coach) Альтернативы: mutable строки с audit log; mutable draft с freeze при подтверждении; line-level append-only versions; event log + current projection; полные document revisions — не единственный вариант
- (idea by coach) Если нужна полная история при меньшем дублировании, можно сделать copy-on-write: document revision ссылается на immutable line versions, неизменённые строки и региональные snapshots переиспользуются между версиями
- (decision by user) Полное восстановление состояния после каждого изменения не требуется; достаточно текущего состояния и существующего глобального audit log

- (question by user) Можно ли отказаться от line segments и оставить одну таблицу товарных строк
- (idea by coach) Однотабличный вариант: каждая document product line сама является owner-сегментом и хранит quantity + from/to owner; один SKU повторяется несколькими строками только при разбиении владельцев, без JSON и дочерней segment table
- (insight by coach) Нельзя одновременно иметь одну физическую таблицу, ровно одну row на SKU и нормализованное многовладельческое разбиение без массива/JSON; однотабличная модель выбирает повтор SKU по owner combination
- (decision by user) Отдельная segment/allocation table не используется; один SKU может повторяться в universal product line только для разных комбинаций from/to owner
- (idea by coach) Unique ключ universal line: document_id + product_id + normalized from_owner pair + normalized to_owner pair; quantity хранится только в этой строке
- (decision by user) Нормализованный regional snapshot остаётся отдельной дочерней таблицей universal product line
- (insight by coach) Failure tradeoff однотабличного owner split: повторные строки одного SKU получают одинаковые product snapshot fields и собственные одинаковые regional snapshot rows; устранить это без отдельной product-snapshot parent table невозможно
- (decision by user) Принято дублирование product и regional snapshots для повторных строк одного SKU с разными owners ради более простой однотабличной line-модели
